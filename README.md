# Sayfold

**Say an idea, get it as text, send it to your repo.** Press record, say it and watch the words appear while you talk, review it as text you can edit, and send it to your own GitHub repo as an issue. Say "no, Tuesday" or "scratch that" and it changes what you said instead of typing it out. What you say is sent to Sayfold's server to be turned into text and edited as you ask, and isn't kept. When the server can't take it, the speech model in your browser does the work instead, and a recording none of which went to the server stays on your device. The text goes straight from your browser to GitHub with your own token.

It's a voice-to-idea inbox (lab#80): GitHub is the API, so the issues are there for you, or for agents, to pick up.

Sayfold understands English. Its speech model is English only, and garbles other languages, so for now it doesn't offer any.

## How it works

1. **Record.** Press the big button, or **Space** on a computer (the page says so where there's a keyboard). A live waveform and a clock show it's listening. A recording stops on its own at 2 minutes.
2. **Live text.** Before you record, the page says in one sentence that what you say is sent to Sayfold's server to be turned into text and edited as you ask, and isn't kept. While you talk, the microphone streams to Sayfold's Worker (see [The Worker](#the-worker)) and the words show under the clock as they're heard: the sentence you're still saying a shade lighter, until it ends. **Stop** waits for the last words and their spoken edits (a few seconds at most), then opens the review.
   - **Spoken edits** (lab#109). Each time you finish a sentence or pause, a language model on the server gets the text so far and what you just said, and sends back the whole text with your edit made. So "Let's meet on Monday at ten. No, Tuesday." becomes "Let's meet on Tuesday at ten.", and "I mean Hannah", "not the phone, the tablet", "change five to ten", "scratch that" and "delete the last sentence" change what's there instead of being typed out. Words that only sound like a command stay as you said them ("No, I don't think the old design was better").
   - **Spoken lists.** Say a list ("Shopping list: milk, bread, eggs and butter", "To do list. Buy milk. Call mom.") and it comes back as a line for its heading and a "- " line for each item, which goes to GitHub as a task list.
   - When the model fails, is slow (over 4 seconds) or answers with something that isn't the text, what you said is kept as it was heard, so dictation always works. The in-browser model (below) has no spoken edits: it types what was said.
3. **When the server can't be used, the speech model in your browser does it.** That's when the server says it's off (its daily allowance is used up, or yours is), it doesn't answer, the connection won't open or drops, or it stops part way (another recording of yours is open, the recording got too long, or the speech service failed). The words that did come are kept, and the browser's model turns only the audio after them into text, so nothing you said is lost or doubled. When the server didn't say how much it heard (the connection dropped, say), the browser's model starts a second before the last words came, as they lag the audio, and the words both heard show once. A short note says so on the recording screen. When the server said it's off before you started, the page says that this recording stays on the device. When it went off during a recording, the page says part or all of that recording was sent, and only says the next one stays on the device.
   - **When the model is fetched:** only when it's needed. A live recording never waits for it. When the server is off, it starts loading as you press Record, as before. When live text stops part way through a recording, it starts loading at that moment, while you're still talking, so it's usually ready by the time you press Stop. Fetching it on every visit just in case would cost every visitor about 45 MB for a fallback most never need.
   - The first time, Sayfold loads its speech model (about 28 MB) and the speech runtime (about 15 to 17 MB) from this site, with a progress bar. The model is kept in your browser's cache storage, so later visits start straight away. It runs in a Web Worker, so the page stays responsive: on WebGPU where the browser has it, otherwise on the CPU with WebAssembly. Sayfold finds where you're speaking, leaves out long silences, and gives the model parts of at most 10 seconds, cut in the pauses (see [Long recordings](#long-recordings)).
4. **Review.** If part of the recording may be missing from the text, the page says so above the buttons. If you said something and then took all of it back ("Buy milk. Scratch that."), the review opens empty and says "Everything you said was scratched. Type your idea above, or record again." The "No words came through" screen, which asks you to check the microphone, is only for a recording in which no words were heard at all. The transcript and a title, taken from its first line or sentence, are both editable. The title follows the text until you write your own. **Copy** copies the title, a blank line and the text as **Send** would send it, with any "- " lines as a task list (the text just once when the title is the whole text, and it says so when there's nothing to copy). **Record again** starts a new recording.
   - **Task lists.** Lines that start with "- " go to GitHub as a task list (`- [ ] Milk`): a spoken list as live text writes them, and you can type them too. Each item is trimmed, loses its full stop or comma and starts with a capital. An empty item (a line that's only "- ") is left out, and is never the title. The title is the words before the list, or its first item when the list comes first. Nothing else makes a list: "list" is just a word ("My shopping list: milk, eggs" is sent as it is, lab#102), and text without "- " lines is sent and copied exactly as it is. This replaces the spoken "list" command (sayfold#4), which only worked when the speech model happened to write "list" between commas or full stops.

     While the text has a list, a quiet preview under it shows how it will look on GitHub; the text stays the one thing you edit.
5. **Send to GitHub.** The first time, **Send to GitHub** (or **Connect GitHub** at the top) asks for:
   - the repo, as `owner/name` or its github.com link;
   - a [fine-grained token](https://github.com/settings/personal-access-tokens/new) for that one repo, with one permission: **Issues: Read and write**. The page says how to make one.

   Sayfold checks with GitHub that the token can see the repo and its issues (`GET /repos/{owner}/{repo}`, then its labels) and says plainly what's wrong if not. The repo's labels then show as chips, with `idea` chosen when the repo has it. **Send to GitHub** creates the issue (`POST /repos/{owner}/{repo}/issues`) with the title, the transcript as its body (with any "- " lines as a task list, and otherwise exactly as it is) and the chosen labels, then links to it, with **Record the next idea**. If GitHub says no (a bad token, no access, issues turned off, a rejected issue, its rate limit, or no connection), the page says what's wrong and the text stays. Offline, the button says it's waiting for a connection and comes back by itself.

If the browser refuses the microphone, there's no microphone, another app holds it, or the browser can't record at all, the page says what happened and what to do.

## Long recordings

Moonshine tiny stops early when a clip holds long silences in a noisy room: a part that starts or pauses in quiet can come back empty, and a long part with a few thinking pauses loses its last sentences (lab#95). Up to then, Sayfold cut recordings into parts of up to 20 seconds and joined whatever came back, so on a long take with pauses the end of an idea could vanish without a word. Measured on 4 voices with 1 to 3 second pauses and room noise (15 sentences each), the 20-second parts dropped up to four sentences at the end of a part on some takes, on WebGPU and on the CPU.

So now (`src/core/segments.ts`, `src/core/transcript.ts`):

- **Speech, not silence.** Each 20 ms of audio is compared with the room's own quiet. Long silences before, between and after the speech are left out, apart from 0.2 seconds either side of it. Where speech and room can't be told apart, nothing is left out.
- **Parts of at most 10 seconds.** A pause of a second or more always ends a part. Shorter pauses keep sentences together up to 10 seconds, and speech without a pause is cut in the quietest moment of the last few seconds. Parts never overlap and every bit of speech is in one, so no word is lost or doubled at a cut. Of the settings measured (parts of 6 to 20 seconds, with and without the cut at long pauses, on the same 180 sentences), 10 seconds with the cut kept the most: 179 of 180, the one miss a misheard word, against 177 for the old 20-second parts. The model also had a quarter less audio to work through.
- **A second try.** A part that comes back far too short (fewer than 0.8 words a second of speech, where people say 2 to 3) is tried once more joined to the part before it (or after it, for the first). In a noisy room the model sometimes can't start on a sentence cold, but carries on into it from the one before. The joined text replaces both only when it has more words.
- **Never silently.** If a part is still too short, the review screen says "Part of the recording may be missing. Check the text before sending." The text that did come through is kept.

A short clip is one part, asked once, as before.

## Privacy

- **What you say** is sent, while you record, to Sayfold's Worker on Cloudflare, which passes it to Cloudflare's Workers AI (the Deepgram Flux model) to be turned into text and sends the words back. For spoken edits, the text so far and each new sentence go to Workers AI's Llama 3.3 70B model, and the edited text comes back. The text lives only in the Worker's memory while you record, and is dropped when the recording ends. Sayfold's Worker doesn't store or log the audio or the text, and every request opts out of Deepgram's model-improvement programme, so it isn't used for training (see [The Worker](#the-worker)). The page says so in one sentence before you record.
- When the server can't be used, the speech model in your browser turns the recording (or the rest of it) into text instead. A recording that never went to the server never leaves your device.
- On your device, the recording lives only in this tab's memory and is gone when you leave the page. So does the text, until you press **Send to GitHub**.
- **Where the idea goes:** only to your own GitHub repo, straight from your browser to GitHub's API (`api.github.com`), when you press Send, never through Sayfold's server. Nothing you type is stored or sent anywhere else.
- **Where the token goes:** only to `api.github.com`, in the `Authorization` header of those requests. It's kept in this tab's memory, gone when you close it, unless you tick **Remember on this device**: then it's kept in this browser's localStorage (`sayfold:github`, with the repo's name) until you press **Forget token**, which clears it from memory and storage in one click. Use a fine-grained token limited to the one repo, with Issues as its only permission.
- The page's Content-Security-Policy lets it reach only its own address (with its live-text WebSocket named too: `wss://sayfold.brightloopapps.com`, `wss://sayfold.erko-erka1.workers.dev`, as Safari doesn't always match `'self'` to `wss:`), `https://api.github.com`, and the lab hub's like counter and analytics (`https://lab.brightloopapps.com`, `https://eu.i.posthog.com`). The browser refuses anything else, so the token and the text have nowhere else to go.
- Every file the page needs (the page, the speech model, the speech runtime) comes from Sayfold's own address. The speech library is set up so it never contacts Hugging Face or a CDN.
- What Sayfold keeps in your browser: the speech model, in cache storage, the random receipt for your like if you like it, and your token only if you ask it to remember it. No cookies.
- Sayfold counts page views, recordings started, transcripts finished (with only the recording's length in buckets of seconds, and whether live text, WebGPU or the CPU did the work) and ideas sent (with nothing else at all), through the lab's shared analytics script, with no cookies. What you say, the transcript, the title, the repo, the labels, the token and whether you have one are never sent. On localhost, `*.workers.dev` previews, and with Do Not Track or Global Privacy Control on, the script isn't even loaded. The [privacy note](https://lab.brightloopapps.com/privacy) lists what's counted.
- The heart in the footer likes Sayfold, with the live count from the lab's anonymous like counter. It stays hidden until the count loads and recording never waits for it.

## The speech model

| | |
|---|---|
| Model | [Moonshine tiny](https://huggingface.co/UsefulSensors/moonshine-tiny) by Useful Sensors, English, 27M parameters: a Whisper-class model about the size of Whisper tiny, made for short live speech. |
| Files | The ONNX conversion by onnx-community, [`onnx-community/moonshine-tiny-ONNX`](https://huggingface.co/onnx-community/moonshine-tiny-ONNX/tree/a6da1241cd305dcd64eab1edbd615f2bb9aabb95), pinned to revision `a6da1241cd305dcd64eab1edbd615f2bb9aabb95`, 8-bit quantized: `encoder_model_quantized.onnx` (7.9 MB) and `decoder_model_merged_quantized.onnx` (20.2 MB), plus the tokenizer and config files. |
| Licence | MIT (Moonshine). |
| Where | Committed under `public/models/moonshine-tiny-a6da124/`, with SHA-256 checksums in `src/stt/model.ts` (the `.onnx` ones are Hugging Face's own). The unit tests check every file against them. `node scripts/fetch-model.ts` fetches them again. |

Why not Whisper: Whisper tiny's smallest decoder file is 29 MB, over the 25 MiB limit for one static file on Cloudflare Workers. Moonshine tiny fits in two files well under it.

The speech runtime is [transformers.js](https://github.com/huggingface/transformers.js) 4.3.2 (Apache 2.0) on [ONNX Runtime Web](https://github.com/microsoft/onnxruntime) (MIT). Its default WebGPU build has a 27 MB WebAssembly file, so Sayfold gives it a smaller one instead (`src/stt/ort.ts`): the JSPI build (16.8 MB, WebGPU and CPU) where the browser supports WebAssembly JSPI (current Chrome and Edge), and the plain WebAssembly build (14.3 MB, CPU) elsewhere. Both are copied from `node_modules` into the build, and no file the site serves is over 25 MiB.

## How it's built

| Part | What it does |
|---|---|
| `src/core/` | Plain TypeScript, unit-tested: `time.ts` (the clock and the 2-minute cap), `resample.ts` (mono, and a windowed-sinc resampler down to 16 kHz, for a whole recording or a batch at a time as it's recorded), `live.ts` (live text: the status, the 80 ms frames of 16-bit audio, the running text, and where the browser's model takes over on each kind of fallback), `segments.ts` (finding speech, cutting it into parts in the pauses, and spotting a part that came back too short), `transcript.ts` (the parts' text in order, with one more try for a part that came back short), `title.ts` (the title from the first line, or the words before a task list, and what Copy copies), `list.ts` ("- " lines as a GitHub task list in the issue's body and what Copy copies, read with plain loops so long pasted text stays quick on every keystroke), `mic.ts` (microphone problems in plain words), `progress.ts` (one progress bar over every file), `likes.ts` (the like heart), `github.ts` (reading the repo you typed, the requests to GitHub's API with plain `fetch`, its labels, and its answers in plain words), `token.ts` (the token in memory, or on this device when asked, and forgetting it). |
| `src/audio/` | `recorder.ts` (the microphone through an AudioWorklet, plus an AnalyserNode for the waveform, handing each batch to live text as it comes) and `capture.worklet.ts` (hands raw samples to the page). |
| `src/stt/` | `worker.ts` (the Web Worker: picks WebGPU or the CPU, loads the model on first use, transcribes), `store.ts` (downloads the model once, checks it and keeps it in cache storage), `config.ts` (keeps the library on Sayfold's own origin), `ort.ts` (the onnxruntime build), `client.ts` (the page's side of the worker). |
| `src/analytics*.ts` | The usage events and their allow-list: `$pageview`, `play_started` when a recording starts, `play_finished` when its transcript is ready, with only `seconds_bucket` and `backend` (`server` when live text did all of it, otherwise `webgpu` or `wasm`), and `idea_sent`, with no properties. |
| `src/server/`, `src/listen/protocol.ts` | The Worker and its live-dictation endpoint (see [The Worker](#the-worker)), and the messages the page and the Worker send each other. |
| `src/csp.ts` | The Content-Security-Policy, which `vite.config.ts` puts in the built page as a `<meta>` tag (the dev server goes without it). |
| `index.html`, `src/style.css` | One page, light and dark from the system, no web fonts. The GitHub setup is a native `<dialog>`, and the labels are real checkboxes. |

The page's own code is about 15 KB of JavaScript gzipped. The speech code (about 600 KB before compression, mostly transformers.js) loads only with the first recording.

## The Worker

Sayfold is a Cloudflare Worker (`src/server/index.ts`). It serves the page's files from `dist/` exactly as before, and has a WebSocket endpoint for live dictation (lab#109), which the page uses for live text.

- **`/api/listen`** (WebSocket, `GET` only). The page sends 16 kHz, 16-bit mono audio. The Worker passes it to Workers AI's Deepgram Flux model (`@cf/deepgram/flux`, with the project names as keyterms) and sends back each turn's running text and its end, in the small protocol in `src/listen/protocol.ts`. At each turn's end it asks the correction model (`@cf/meta/llama-3.3-70b-instruct-fp8-fast`, `src/server/correct.ts`) for the whole text with the turn applied, and sends that as a `text` message, which replaces the words so far on the page. The prompt and its rules come from the lab#109 spike. A reply that fails, takes over 4 seconds, or is junk (empty, much longer than the text, a preamble or note, markdown other than "- " lines, or most of the text gone with no "scratch that" or the like in the turn) keeps the turn's plain text. After stop, the Worker waits up to 4 seconds for the last correction before it closes. Every request opts out of Deepgram's Model Improvement Program (`mip_opt_out`), so what a visitor says isn't used for training. It takes only pages on Sayfold's own addresses and localhost.
- **`/api/listen/status`** says whether the page may use it now: `{ "available": true }` or `false`.
- **Limits** (`src/server/config.ts`): one recording at a time and 3 minutes a day per visitor, 2 minutes per recording, and the whole site stops at an estimated 9,000 neurons a day, before Workers AI's free 10,000. A recording counts its seconds of audio or of time connected, whichever is more, plus the correction model's neurons (from the reply's token usage at Workers AI's price, or estimated at 4 characters a token when it isn't given), and one that sends no audio for 10 seconds is closed. Workers AI's free allowance is shared by the whole account, so if it refuses because the day's allowance is used up (error code 3036, a message in its `AiError: 3036: …` form, or its "daily free allocation" wording, when opening Flux, as an error from Flux part way, or from the correction model), Sayfold stops asking it until midnight UTC. A 3036 anywhere else in a message ("timeout after 3036 ms") doesn't count. Then, or if Workers AI fails, the page gets a `fallback` message, with how many seconds of audio the server took, and the socket closes, so the page can use the in-browser model for the rest. The cap resets at midnight UTC.
- **What it keeps:** one Durable Object (`src/server/meter.ts`, SQLite) holds the day's neuron estimate, each visitor's seconds, the recordings open right now, and the day's random salt. A visitor is known only by an HMAC-SHA-256 of their IP address and the date under that salt. An alarm at midnight UTC deletes earlier days' salts and counts, even when nobody has used it, and sets the next one even if that sweep fails. Audio, text, the correction model's prompt and its reply pass through memory only: they're never stored, logged or put in an error, and Workers Logs is off.
- **Tests** mock the AI binding and never call Workers AI, whose free allowance the whole account shares. They run the counter on a real SQLite database, and check that recognisable audio and text never reach storage, a log or another request, with the correction model answering well, with junk, with an error quoting the prompt, too late, and with the day's refusal.

## Run it

```sh
# needs Node 22.18 or newer (the tests run TypeScript directly)
npm install
npm run dev                         # local dev server
npm test                            # unit tests (node --test), Workers AI mocked
npm run build                       # typecheck, then build to dist/
```

The playtest records in a real browser with a fake microphone playing `tests/fixtures/idea.wav`, a clip made with macOS `say`, and checks the transcript has the words in it. `tests/fixtures/list-commas.wav` is a list said the old way ("List. Milk. Bread. End list."), also made with `say`. A second clip, `tests/fixtures/long-idea.wav`, is 48 seconds of fifteen different sentences with thinking pauses (also made with `say`, the command is in `tests/playtest.ts`), played with a room's noise mixed in. GitHub's API is a stand-in inside the playtest (Playwright routes), with a made-up token: it never uses a real token or the live API. So are Sayfold's own `/api/listen/status` and `/api/listen` WebSocket (`page.routeWebSocket`): a scripted stand-in server answers, so the playtest never reaches the real Worker or Workers AI, whose free allowance the account shares. Most checks hear "unavailable" from the status, so they test the in-browser model as before.

# PLAYTEST_BROWSER  Chromium-based browser executable (default: Brave; falls back to Playwright's Chromium)
